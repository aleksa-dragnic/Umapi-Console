# 0006 - API types are generated from the deployed document, committed, and checked for drift outside the required checks

- **Status:** Accepted
- **Date:** 2026-09-25
- **PR:** #7

## Context

Every request the console makes crosses into an API it does not control. The
paths, parameters and body shapes have to come from somewhere, and whatever that
source is decides whether a change on the API side is noticed before a reviewer
notices it in the browser.

The deployed instance serves an OpenAPI 3.1 document at `/openapi/v1.json`
(`docs/OBSERVED-BEHAVIOUR.md` row 59). It is complete about paths, operations,
parameters and request and response bodies. It is not complete about behaviour:
it omits the problem-details fields the console reads, documents the HATEOAS
media type with the wrong body, spells the entity status as an open string, lists
no 429, 413 or refresh 409, and describes no security scheme (rows 60-62).

The document lives on a free instance that sleeps when idle and takes about half
a minute to answer (row 35), and that can be down. Whatever checks the contract
depends on it being up.

## Decision

`src/lib/api/schema.d.ts` is generated by `openapi-typescript` from the
deployed `/openapi/v1.json` with `pnpm api:generate`, committed, and never
edited by hand. `.prettierignore` excludes it, so formatting cannot change it.

A `contract` job in `.github/workflows/ci.yml` wakes the instance, regenerates
the file and fails if the result differs from what is committed. It runs on
every pull request, every push to `main`, weekly, and on demand. It is **not** a
required check: `build-and-test` and `e2e` remain the only ones.

Requests go through one `openapi-fetch` client, `src/lib/api/client.ts`, created
with `credentials: 'include'` and a `fetch` that is looked up on every request.
Its base URL is the API origin with no path, from `VITE_API_BASE_URL`, and the
deployed instance when that is unset.

The generated types are the contract for shapes. Behaviour the document does not
state - statuses it does not list, problem-details fields it omits - comes from
`docs/OBSERVED-BEHAVIOUR.md`, never from the types.

## Alternatives considered

### Types written by hand

Nothing would notice when the API changes. The console's types would describe
what someone remembered the API to be, and a renamed field would surface as
`undefined` at runtime rather than as a type error or a red check.

### Generated at build time and not committed

Every build, local and CI, would need the instance to be up and awake, and a
cold start would add half a minute to each. A pull request could not show what
changed in the contract, because the types would not be in the diff.

### A committed snapshot of the document, generated offline

Deterministic and fast, but the snapshot is exactly the thing that goes stale:
it would record what the API said on the day it was taken, and the check would
compare the types against the snapshot instead of against the API.

### The drift check as a required check

It would make the contract impossible to ignore, and it would also make every
merge wait on a free instance's uptime. A failure there says the API moved or is
down - both worth seeing, neither a reason the console's own change is wrong.

### A generated client with classes per operation

Heavier, and it generates code rather than types. `openapi-fetch` adds a few
kilobytes and keeps every call a plain `fetch` the inspector can observe.

## Consequences

A change to the deployed document turns the `contract` check red on the next
pull request, push or Monday, with the diff in the log. The fix is
`pnpm api:generate`, a reviewed diff, and whatever the new types break.

A red `contract` check does not block a merge. Merging while it is red is a
decision to be made on purpose, and the pull request says why.

The document's gaps stay gaps in the types. The error reader, the handlers of
429, 413 and the refresh 409, and the entity status's four values are written
from the observed rows, and the mock (PR 8) implements the rows, not the
document. Query parameters are sent under the names the document gives them,
in PascalCase (row 64).

Because `fetch` is resolved per request, anything that replaces
`globalThis.fetch` after the client exists - the mock layer in tests - sees
every call. `src/lib/api/client.test.ts` asserts this, along with
`credentials: 'include'` and the joined URL.

The deployed origin is written in two places, `package.json`'s `api:generate`
and the `contract` job's `API_ORIGIN`, and a third time as the client's default.
When the API moves to `api.<domain>` in M5, all three change together.
